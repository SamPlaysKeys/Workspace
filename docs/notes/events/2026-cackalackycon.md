### Session 10 {#session-10}

| Field | Value |
|-------|-------|
| **Speaker(s)** | Jesse Jenter |
| **Title** | Bring Out Your Dead: The Art and Science of JavaScript Exploit Necromancy |
| **Room** | Main Talk Room |
| **When** | Fri 3:00 pm - 3:50 pm ET |
| **Sessionize ID** | 1134157 |

#### Description

Archives like Google Project Zero are full of "digital rot." We all have folders of legendary JS exploits from old CTFs or bugs saved that simply will not fire anymore. Most of the time, the bug isn't even patched; the exploit is just dead because of environmental drift.

I have spent the last year building a way to autopsy these broken PoCs and surgically repair them at scale. This talk is the result of an investigation into 13,780 execution attempts across 53 versions of V8. I will break down the three forces driving the "A-PoC-alypse" (Flag Drift, Syntax Barriers, and Dependency Tangles) and show a two-stage approach to resurrection.

We will look at the "Surgical Repair Loop," a heuristic-driven process that autopsies failure signatures to map flags and bridge syntax barriers while protecting the engine-specific "magic" (V8 intrinsics) the exploit actually relies on. Finally, I will introduce the Groundskeeper: a secondary diagnostic pass that interprets opaque exit codes to prove exactly why an exploit is permanently dead, reaching 98% diagnostic clarity on the entire problem space.

I am coming with the data-backed results for resurrecting code that everyone else gave up on, moving reproduction rates from a dismal 21% to 82% for aligned artifacts.

What will the audience learn?

->Automated Healing: How to fix the Three Pillars of exploit decay.

->Diagnostic Mastery: Turning a useless "Exit Code 1" into a roadmap of what is actually broken.

->Exploit Fidelity: Strategies for keeping historically significant exploit code functional as engines evolve.

#### Description

After retiring from a 20-year career as a Special Forces Green Beret , I thought my next chapter would be a seamless continuation of the last: stay relevant, maintain my clearance, and keep operating in familiar circles. Instead, within days of retirement, life forced a reset. A family medical crisis, the loss of institutional identity, and later being replaced on a course I built from the ground up forced me to confront a hard truth: purpose doesn’t transfer automatically — it must be rebuilt.

This talk is not about tactics or tools. It’s about ownership.

I’ll share the realities of transitioning from elite military service into entrepreneurship, the early paralysis that kept me from pursuing customers, the mistakes that nearly crushed my business when I said “yes” to everyone, and the discipline required to narrow focus and define an ideal customer. This session is for students, veterans, founders, and early-career professionals who feel behind, unsure, or stuck. You don’t need permission. You need motion. Stop waiting. Start building.

### Session 17 {#session-17}

| Field | Value |
|-------|-------|
| **Speaker(s)** | Xenia Mountrouidou |
| **Title** | From LLM Apps to Agentic Workflows for Security: Evaluation is All You Need |
| **Room** | Main Talk Room |
| **When** | Fri 6:30 pm - 6:55 pm ET |
| **Sessionize ID** | 1141626 |

#### Description

There is significant pressure within the Security Operations Center (SOC) to leverage AI Large Language Models (LLMs) for automating routine tasks. Specifically, the use of automated agents to streamline workflows and handle these "boring things" has become a popular trend. - Why this stack works well against accidental LLM mistakes but fails against intentional adversarial input

- Brief framing: we've built an immune system that can be turned against the host

2. Attack: Poisoning Context Files (12 min)

- CLAUDE.md files tell AI agents how to behave in a codebase. They're the instruction set for every AI review agent and coding assistant

- Demo: A malicious contributor submits a PR that subtly modifies CLAUDE.md to instruct the AI review agent to treat certain vulnerability patterns as acceptable

- Demo: Embedding hidden instructions in CLAUDE.md that only activate when the file is processed by an LLM (invisible to human reviewers scanning the diff)

- The trust problem: CLAUDE.md is both human-readable documentation and machine-executable instructions, and those two roles conflict

3. Attack: Manipulating AI Code Review Agents (12 min)

- CI-integrated LLM review agents (Claude Code Action, GitHub Copilot reviews) process PR diffs as input, which makes them prompt injection targets

- Demo: Crafting code comments and variable names that manipulate the review agent into ignoring a vulnerability in the same PR

- Demo: Exploiting context window limitations, submitting a large PR where the security-critical change is buried beyond what the agent actually analyzes

- How multi-agent review architectures (separate security agent vs. code quality agent) change the attack surface but don't eliminate it

4. Attack: Weaponizing the Trust Boundary (8 min)

- Developers trust AI review agent approvals the same way they trust human reviewer approvals but the threat model is completely different

- Demo: A PR that passes all automated AI security checks (bandit, semgrep, CodeQL, AI review) while containing an exploitable vulnerability that only manifests at runtime

- The "security theater" problem: when AI tools give a false sense of comprehensive review, human reviewers do less scrutiny, not more

- Supply chain angle: what happens when a dependency update introduces a poisoned CLAUDE.md or .github/copilot-instructions.md in a transitive dependency

5. Defenses That Actually Work (10 min)

- CODEOWNERS and integrity protection for context files treat CLAUDE.md like you treat CI config

- Security invariant tests that assert properties rather than relying on review (auth on every endpoint, parameterized queries, no unauthenticated routes without explicit annotation)

- Separating security rules from LLM-accessible context. keep critical security requirements in CI configuration that PRs can't modify, not in files the LLM reads

- Architectural defenses: read-only review agents, limited tool access, separate security review with independent context

- The human-in-the-loop problem: practical strategies for maintaining meaningful human review when AI tools handle the first pass

6. Takeaways & Q&A (3 min)

- Your AI security tools need their own threat model

- Context files are code protect them like code

- Defense in depth means layers that can't compromise each other

- Pointers to open-source repos with all attack and defense examples
