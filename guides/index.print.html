Clean-Room Reverse-Engineering Findings from Stock Google Jamboard ROM

Overview

This document records the clean-room interoperability findings obtained from inspecting partition backups (stock-system.img, stock-vendor.img, and stock-wifi-rp3.img) pulled from a Google Jamboard (baracus) running Google’s final End-of-Life Android 7.0 release (google/baracus/baracus:7.0/NRT1.240624.004/12020658:user/release-keys).

The primary goal of this investigation was to determine how Google’s stock OS distinguished between fingers, the passive stylus, and the passive microfiber eraser (or any other eraser/palm), and why unmodified AOSP/LineageOS and mainline Linux kernels only expose basic finger touch.

Status note (live capture update): The stock-ROM analysis below was done statically. Live captures on LineageOS later showed that the RAPT firmware classifies each contact itself, and that the 0.40 / 0.475 size bands described in section 3 do not line up with the live Width/Height values. See live-input-capture-findings.md for the measured behavior, which is what jamboard-pen-daemon uses. Stylus tilt/wedge handling is out of scope for now.

Clean-Room & Interoperability Scope: This document contains only factual hardware interface specifications, USB HID descriptor structures, UART command framing, and functional descriptions required to build independent open-source Linux/Android drivers for user-owned EoL hardware. No proprietary binaries, firmware blobs, or copyrighted source code are reproduced.

2. The Smoking Gun: Why Stylus & Eraser Fail on Unpatched Linux / LineageOS

Tracing the touch data path from the USB wire all the way to the whiteboard renderer revealed three connected architectural facts:

Finding A: RAPT Hardware Reports Contact Geometry and Class Over HID

/system/etc/rapt_hid_descriptor.bin (2,313 bytes) defines the exact USB HID Report Descriptor for the RAPT Touch InGlass controller (VID:PID 1cbe:0003).

  • Primary touch streaming uses Input Report 0xF1 (241), which is 340 bytes long and carries 24 fixed 14-byte contact slots plus Contact Count (1 B) and Scan Time (2 B).
  • Every contact slot is wrapped inside a standard Logical Collection (Finger, 0x000D:0x0022) containing Tip Switch, Contact ID, X, Y, Width (0x0D:0x48), Height (0x0D:0x49), Tip Pressure (0x0D:0x30), and—at contact bytes +12..+13—a 16-bit vendor-defined field (Usage Page 0xFF00, Usage 0x01, range 0..14999).
  • Because touchdaemon simply forwards raw /dev/hidraw* reports to /dev/hidg0 using rapt_hid_descriptor.bin and no user-space daemon injects uinput events on stock Android, all contact geometry already arrives over USB in Input Report 0xF1. (Live captures later showed the tool class itself is carried in Vendor 0xFF00:0x02 on a second, extended HID interface, and is also encoded in the Width field. The 0xFF00:0x01 field in the basic layout is just a copy of Height.)

Finding B: Unpatched hid-multitouch.c Drops 0xFF00:0x0001 and Hardcodes MT_TOOL_FINGER

Comparing rapt_hid_descriptor.bin against upstream Linux and LineageOS/android_kernel_nvidia_linux-4.9 (drivers/hid/hid-multitouch.c):

  1. hid-multitouch has no quirk or handler for 0x1cbe:0x0003 or 0xFF00:0x0001, so mt_touch_input_mapping() ignores bytes +12..+13 (return 0).
  2. Because each slot’s enclosing HID collection is HID_DG_FINGER (0x000D:0x0022), mt_process_slot() unconditionally reports ABS_MT_TOOL_TYPE = MT_TOOL_FINGER (0) for every contact—whether finger, passive stylus, or physical eraser.

Finding C: Stock libinputflinger.so Added a Custom MT_TOOL_ERASER = 3 Mapping

Inspecting /system/lib64/libinputflinger.so showed that Google customized Android’s InputFlinger specifically for the Jamboard’s kernel driver:

  • In standard AOSP, ABS_MT_TOOL_TYPE only defines 0 (MT_TOOL_FINGER), 1 (MT_TOOL_PEN), and 2 (MT_TOOL_PALM). Standard AOSP cannot produce AMOTION_EVENT_TOOL_TYPE_ERASER (4) from ABS_MT_TOOL_TYPE alone without BTN_TOOL_RUBBER.
  • In Jamboard’s stock libinputflinger.so (MultiTouchInputMapper::syncTouch @ 0x4d9e0, lookup table @ 0x55e40), Google extended the ABS_MT_TOOL_TYPE translation table to 4 entries (0..3):
    • 0 → 1 (AMOTION_EVENT_TOOL_TYPE_FINGER)
    • 1 → 2 (AMOTION_EVENT_TOOL_TYPE_STYLUS)
    • 2 → 0 (AMOTION_EVENT_TOOL_TYPE_UNKNOWN, falling back to BTN_TOOL_*)
    • 3 → 4 (AMOTION_EVENT_TOOL_TYPE_ERASER)
  • Stock libinputflinger.so also includes spatial/temporal eraser latching (TouchInputMapper::trackToolSwitch / NVPreProcTouchInput, controlled by system properties input.ptr_trk.eraserlatch_range and input.ptr_trk.eraserdelay_time) to prevent a lifted or bouncing eraser puck from briefly flickering to finger/stylus tool types within a bounding box.

Implication for LineageOS & Fedora GNOME: Rather than patching custom non-standard ABS_MT_TOOL_TYPE = 3 values into both the kernel and Android/Wayland compositors, a clean user-space daemon (jamboard-pen-daemon) reading /dev/hidraw* can split fingers onto a multi-touch uinput screen device and emit stylus/eraser contacts onto a dedicated uinput direct tablet device using standard Linux BTN_TOOL_PEN and BTN_TOOL_RUBBER—which both unmodified LineageOS (TouchButtonAccumulator) and unmodified Fedora GNOME Wayland (libinput tablet tool) understand natively out of the box.

3. How Stock Jamboard Handled Universal Erasers & Palm Wiping

Inspecting the unobfuscated Protobuf schema com.google.apps.pectin.android.proto.Touch$TouchPoint in classes2.dex (PectinContainer.transferTouchMotionEventToPectin) alongside libjamkiosk.so revealed how Google supported any physical dry-erase block, the heel of a palm, and stylus stroke width:

1. Stock PectinContainer Touch Schema (Touch$TouchPoint)

When JamKiosk translates an Android MotionEvent into its native C++ stroke engine (pectin::platform::android::PectinContainer::Respond), it populates only:

  • id_ (field 1): MotionEvent.getPointerId(i)
  • type_ (field 2): BEGIN (1), MOVE (2), STAY (3), END (4), CANCEL (5)
  • toolType_ (field 3): FINGER (1) or STYLUS (2) only (MotionEvent.getToolType(i) == 2 ? STYLUS : FINGER — Touch$TouchPoint has no ERASER enum value!)
  • x_ / y_ / lastX_ / lastY_ (fields 4..7): getX(i), getY(i), and previous coordinates
  • size_ (field 8): MotionEvent.getSize(i) (computed by Android TouchInputMapper::cookPointerData as 0.5 * (rawTouchMajor + rawTouchMinor) / 14999.0)
  • timestamp_ (field 9): MotionEvent.getEventTime()
  • pressure_ (field 10): MotionEvent.getPressure(i) (optional float from RAPT HID Tip Pressure 0x0D:0x30)

(Note: A generic Lagsr; compatibility helper in classes14.dex references getTouchMajor and getOrientation, and PolylinePacker::AddPoint retains ribbon-orientation code, but Jamboard’s active PectinContainer bridge never calls AXIS_TILT or getOrientation.)

2. Open-Ended Universal Eraser Size Bands (DrawingController::TouchTypeFromSize @ 0x00474714)

On Jamboard hardware (pectin::device::Device::type == 3, initialized unconditionally at 0x00280e24), DrawingController::TouchTypeFromSize(float size) classifies MotionEvent.getSize(i) against two normalized float thresholds with no upper cap:

  • size < 0.40f (0x3ecccccd) → 2 (Stylus / Draw): Fine-tip strokes route to UpdateDataFeedsWithTouchPoint (0x00475048).
  • 0.40f <= size < 0.475f (0x3ef33333) → 1 (Finger): Standard touch/UI manipulation—or finger-wipe erasing when CanUseFingerEraser() (KioskSettingsManager::FingerEraser) is enabled.
  • size >= 0.475f (open-ended [0.475f, 1.0+], no upper bound) → 3 (Universal Eraser): Routes to UpdateEraserTouchGroups (0x00474754). Because there is no upper size limit, Google’s official microfiber puck, any third-party felt whiteboard eraser, a folded cloth, or the heel/side of a user’s palm all trigger hardware-class erasing identically.

Live-data caveat: On the LineageOS unit, 0.5 * (Width + Height) / 14999 is 0.40 for stylus, 0.90 for finger and 1.00 for eraser contacts. Stock Google’s kernel therefore remapped these fields in a way we have not seen (its LNX boot image was not dumped), so these exact thresholds cannot be applied to raw RAPT values.

3. Multi-Contact Palm & Whiteboard-Block Clustering (UpdateEraserTouchGroups @ 0x00474754)

Because a palm wipe or a worn rectangular whiteboard eraser often splits into multiple adjacent IR shadow blobs (e.g., palm heel + knuckles, or two edges of a felt block):

  • Spatial Capture Radius (200.0f * dpi_scale px @ 0x004749e8, ~63 mm on the 55" 4K panel): Any contact landing within 200 px of an active eraser TouchGroup::GetCenterPoint() (0x00476da8) is merged into that same TouchGroup (TouchGroup::AddPoint @ 0x00476d50) rather than spawning stray finger gestures or pen strokes.
  • Dynamic Swath Width (TouchGroup::GetRadius @ 0x00476e04 & EraserRenderer::CalculateStrokeThickness @ 0x004a5dd0): GetRadius() computes the maximum Euclidean spread (max_i hypot(pt_i - center), capped at 450.0f px @ 0x00475e20) across all contacts in the group and scales the eraser brush dynamically: $$\text{thickness} = 28\text{ px} + 2.0 \times \text{group_radius} + 0.001 \times \text{speed}^2$$

4. Stylus Stroke Width via Optical Tip Pressure

Because an optical InGlass bezel measures infrared beam occlusion rather than mechanical downward force, RAPT’s Tip Pressure (0x0D:0x30, 0..29999) tracks contact area, not force. Stock JamKiosk feeds MotionEvent.getPressure(i) (TouchPoint.pressure_) into LocalDataFeed::AppendPoint (0x0052b3fc) -> ParticleRenderer::FeedPoint (0x004b57e8), interpolating stroke width between min_width and max_width.

jamboard-pen-daemon passes Tip Pressure through as ABS_PRESSURE (256..4095) for the stylus, and maps the eraser cluster span into ABS_PRESSURE (1200..4095) while BTN_TOOL_RUBBER is active. It does not synthesize tilt axes.

Fedora Workstation (GNOME) & Stylus/Eraser Bring-Up Plan for Google Jamboard

Overview

This guide documents the end-to-end hardware architecture, reverse-engineering workflow, and installation procedure for running stock Fedora Workstation (aarch64, GNOME on Wayland)—with full multi-touch, passive stylus, physical eraser, and display backlight support—on a Google Jamboard (codename baracus).

Because the Jamboard’s passive stylus and eraser currently lack complete tool-type/eraser handling in open-source ROMs, this plan uses a two-stage execution strategy:

  1. Stage 1 (LineageOS Lab & Protocol Capture): Unlock the bootloader, back up Google’s stock Android 7 partitions (preserving proprietary calibration, firmware, and the stock Jamboard APK’s optical touch math), boot LineageOS 22 (baracus_tab), and capture raw USB HID / evdev optical sensor data over Root ADB to build a universal uinput pen/eraser daemon.
  2. Stage 2 (Fedora Workstation aarch64 Bring-Up on Internal eMMC): Chainload a UEFI-enabled U-Boot from Google’s signed cboot bootloader, deploy stock Fedora Workstation (GNOME Wayland) 100% onto the internal 16 GB eMMC (CAC for /boot/efi, APP for /boot, and UDA with zstd Btrfs compression for /), and enable the Jamboard hardware daemons (touchscreen GPIO init, UART scaler brightness, and the pen/eraser translator).

Hardware Architecture & Reference Map

Compute & Carrier Subsystems

  • SoC Module: Standard 400-pin Samtec NVIDIA Jetson TX1 (Tegra210 / T210) module on a custom Google/BenQ carrier board (id=2180, sku=9999).
    • CPU / RAM / Storage: 4x ARM Cortex-A57 @ 1.9 GHz (aarch64), 4 GB LPDDR4, 16 GB internal eMMC (sdhci-tegra.3 / sdhci@700b0600).
    • GPU: 256-core NVIDIA Maxwell (gm20b), supported upstream by tegra-drm + nouveau.
  • 55" 4K 60Hz Display & MStar MST9U23T1 Scaler:
    • Video path: Tegra X1 sor1 HDMI output → internal carrier HDMI → MStar MST9U23T1 scaler → 51-pin eDP to the 4K LCD panel.
    • External video inputs (2x HDMI + side USB-C DisplayPort alt-mode) also feed into the MStar scaler.
    • Backlight & Input Switching: There is no PWM/GPIO/DDC backlight. Brightness, video source switching, and speaker unmuting are controlled via 9600-baud UART commands sent over /dev/ttyTHS1 (serial@70006040).
  • Optical Touchscreen (“HazelRed” / hazeldos — RAPT Touch InGlass):
    • 100–120 Hz infrared optical waveguide bezel driven by an internal NXP/RAPT Touch controller (VID:PID 1cbe:0003) wired to internal USB host port usb-70090000.xusb-4 (usb2-3 UTMI).
    • Passive Stylus & Eraser: Neither accessory contains electronics or batteries. The bezel measures the physical 2D optical shadow/ellipse on the glass (~1.5–3 mm fine stylus tip, ~8–15 mm finger, ~40–60 mm eraser puck).
    • Power/Boot Sequence Required: On every boot, the host must toggle three Tegra GPIOs (pwren=174 / V6, bootmode=184 / X0, reset=185 / X1) to boot the touch MCU from SPIFI flash before it enumerates on USB.

Prerequisites

Hands-On Operator Workstation & Gear

  • Linux or macOS laptop with current android-platform-tools (adb, fastboot, and img2simg / android-tools) plus a Linux environment (native or VM) with btrfs-progs, dosfstools, rsync, and losetup for Stage 2 image assembly.
  • Known-good Micro-USB data cable (verify it passes data, not power-only) connected to the Jamboard’s rear Micro-USB port.
  • Wired USB keyboard (and mouse) plugged into a side USB 3.0 Type-A port.
  • At least 35 GB of free disk space on the build computer (to hold the ~15 GB stock partition backups plus the unpacked Fedora raw image and sparse UDA image).
  • Jamboard Passive Stylus and Jamboard Physical Eraser on hand for Stage 1 testing.

Required Downloads for Stage 1 (LineageOS)

  1. LineageOS baracus_tab (Tablet variant — strongly preferred over Android TV baracus):
    • Download dtb.img, recovery.img, and the latest lineage-22.2-*-baracus_tab-signed.zip from the LineageOS baracus / baracus_tab downloads page.
    • (Why baracus_tab instead of baracus?) baracus is an Android TV build that requires pairing a Bluetooth remote to navigate setup; baracus_tab is standard tablet Android and works immediately with touch/mouse/keyboard.
  2. (Only if the Jamboard is NOT already on Google’s final EoL Android 7.0 release NRT1.240624.004/12020658):
    • Google’s final OTA a40bffa0422296aa577c32d91fdf9f546301ce9c.zip + stock recovery/DTB (see LineageOS baracus install wiki).

Stage 1: Unlock, Backup Stock ROM, & Reverse-Engineer Stylus/Eraser on LineageOS

Step 1.1: Verify Stock Firmware Build

  1. Boot the Jamboard into stock Android 7.0.
  2. If stuck on the unlicensed kiosk splash screen, plug a USB keyboard into the side USB-A port and press Super + N (Windows + N) or open notifications/Settings.
  3. Navigate to Settings → About and confirm the build number ends in NRT1.240624.004 (12020658).
    • If on an older build, follow the LineageOS Wiki firmware update instructions before proceeding.

Step 1.2: Enter Fastboot & Unlock the Bootloader

  1. Power off the Jamboard completely.
  2. Plug the Micro-USB cable from your computer into the rear Micro-USB service port.
  3. Hold the Power button for ~4 seconds until the cboot Fastboot menu appears on screen.
  4. On your computer, confirm connectivity:
    fastboot devices
  5. Unlock the bootloader:
    fastboot oem unlock
  6. Use the physical Volume buttons on the Jamboard to highlight confirmation and press Power to confirm.
    • Important: fastboot oem unlock only wipes UDA (userdata) and CAC (cache). Google’s stock APP (/system), vendor, and RP3 partitions remain completely intact!

Step 1.3: Flash LineageOS Recovery & Back Up Stock Google Partitions (CRITICAL — DO NOT SKIP!)

Before installing LineageOS (which overwrites APP /system), boot into LineageOS Recovery to pull a full bit-for-bit backup of Google’s stock system, vendor, and Wi-Fi calibration partitions.

  1. Re-enter Fastboot mode (hold Power for 4 seconds from off) and flash LineageOS’s dtb.img and recovery.img:
    fastboot flash dtb dtb.img
fastboot flash recovery recovery.img
  2. On the Jamboard’s cboot screen, use the Volume buttons to highlight “Boot recovery kernel” and press Power.
  3. Wait 5–10 seconds for LineageOS Recovery to initialize the display and touchscreen.
  4. In LineageOS Recovery, go to Advanced → Enable ADB.
  5. On your computer, create a backup folder and pull the raw stock partitions:
    mkdir -p ~/jamboard-stock-backup && cd ~/jamboard-stock-backup

adb root || true
adb shell ls -l /dev/block/platform/sdhci-tegra.3/by-name/

# Pull Wi-Fi MAC/calibration, vendor blobs, boot/dtb, and stock Google /system
adb pull /dev/block/platform/sdhci-tegra.3/by-name/RP3    stock-RP3-wifi.img
adb pull /dev/block/platform/sdhci-tegra.3/by-name/DTB    stock-DTB.img
adb pull /dev/block/platform/sdhci-tegra.3/by-name/LNX    stock-LNX-boot.img
adb pull /dev/block/platform/sdhci-tegra.3/by-name/vendor stock-vendor.img
adb pull /dev/block/platform/sdhci-tegra.3/by-name/APP    stock-APP-system.img

sha256sum *.img > SHA256SUMS.txt

    Why stock-APP-system.img is essential: Mounting this ext4 image gives us /system/usr/idc/*.idc (Google’s exact touch calibration), /system/bin/scalerdaemon (all 66 UART scaler/audio/input commands), libinputflinger.so, and the stock Google Jamboard APK—which contains Google’s exact mathematical formulas and size thresholds for stylus, stroke width, palm rejection, and physical eraser detection!

Step 1.4: Install LineageOS 22 (baracus_tab) & Enable Root + Wireless ADB

  1. Still in LineageOS Recovery on the Jamboard:
    • Tap Factory reset → Format data/factory reset and confirm.
    • Return to the main menu and tap Apply update → Apply from ADB.
  2. Sideload the LineageOS baracus_tab package from your computer:
    adb sideload lineage-22.2-*-baracus_tab-signed.zip
  3. Tap Reboot system now.
  4. Once booted into LineageOS:
    • Connect to Wi-Fi.
    • Go to Settings → About tablet and tap Build number 7 times to unlock Developer Options.
    • Go to Settings → System → Developer options and enable:
      • USB debugging
      • Rooted debugging (critical — lets adb root inspect /dev/hidraw*, /dev/input/*, and /sys/kernel/debug/hid)
      • Wireless debugging / ADB over network (optional, lets you disconnect the rear Micro-USB cable and connect via adb connect <JAMBOARD_IP>:5555).

Step 1.5: Reverse-Engineering the Stylus & Eraser Protocol

Background Findings Driving the Investigation

  • The RAPT Touch USB device (1cbe:0003 at usb-70090000.xusb-4) exports large USB HID Report Descriptors (2,313 B and 3,149 B) and multiple USB HID interfaces (input0 and input1).
  • Currently, LineageOS silences input1 by mapping it to non-existent display="99" in input-port-associations.xml because both interfaces fire concurrently.
  • Furthermore, standard hid-multitouch reports contacts as generic touches with ABS_MT_TOUCH_MAJOR/MINOR and no tool type, which neither AOSP nor GNOME automatically promotes into a hardware Stylus or Eraser. The live unit also exposes a second, extended 3,149-byte HID interface carrying the firmware tool class.

Mount stock-APP-system.img read-only to extract Google’s reference configs and binaries:

# 2. Full 2,313-byte HID Report Descriptor(s) and live HID debug state
adb shell 'for f in /sys/kernel/debug/hid/*/rdesc; do echo "=== $f ==="; cat "$f"; done' > hid-rdesc.txt

(Inspect hid-rdesc.txt with hid-recorder / hidrd-convert to enumerate every Digitizer, Pen, Eraser, Width/Height, Azimuth, and Vendor 0xFF00 usage across input0, input1, and /dev/hidraw*.)

C. Guided Live Capture (rapt-live-probe.sh)

Enable Developer options > Rooted debugging, run adb root, then use the helper script from this repo. It finds the extended RAPT hidraw interface, records five phases (finger, stylus, eraser/whiteboard block, palm, stylus + resting palm) as CSVs, and prints per-class statistics:

PROBE_SECS=12 ./artifacts/jamboard/rapt-live-probe.sh ./jamboard-probe-results

The measured results from this procedure are in live-input-capture-findings.md. The key result: the RAPT firmware classifies contacts itself (1 stylus, 2 finger, 3 eraser/large) and Width + Height is constant per class, so no size-guessing geometry is required.

D. Universal jamboard-pen-daemon (hidraw -> uinput)

artifacts/jamboard/jamboard-pen-daemon.c is a small static C daemon that works identically on both LineageOS and Fedora GNOME:

  • Reads RAPT hidraw frames directly (extended interface preferred) and grabs the raw evdev nodes with EVIOCGRAB so duplicate events never leak to the OS.
  • Exposes two clean Linux uinput devices (INPUT_PROP_DIRECT):
    1. Jamboard RAPT Finger Touch: finger-class contacts as 24-slot multi-touch.
    2. Jamboard RAPT Stylus & Eraser: stylus-class contacts -> BTN_TOOL_PEN + BTN_TOUCH + ABS_X/Y/PRESSURE; eraser-class contacts (any eraser, felt block, or palm) -> BTN_TOOL_RUBBER with spatial clustering so palm wipes do not leak finger gestures.
  • Result: Android (TOOL_TYPE_STYLUS / TOOL_TYPE_ERASER) and Fedora GNOME Wayland (libinput tablet tools) switch between Pen, Finger, and Eraser with no per-app hacks. Stylus tilt/wedge handling is not implemented (the optical bezel reports no tilt).

Common Pitfalls

  • Plugging into the side USB-C port for Fastboot/ADB: The side USB-C port is wired exclusively to the MStar display scaler as a DisplayPort video input. Always use the rear Micro-USB service port for Fastboot and wired ADB.
  • Formatting /system before pulling stock-APP-system.img: Once LineageOS is sideloaded, Google’s stock /system (APP) is overwritten. Always pull APP, vendor, and RP3 from LineageOS Recovery immediately after fastboot oem unlock before wiping or sideloading.
  • Flashing baracus (Android TV) instead of baracus_tab (Tablet) without a Bluetooth remote: The baracus TV build locks initial onboarding behind a Bluetooth remote pairing screen. Use baracus_tab for touch/mouse operation.
  • Flashing an unsparsed 9.4 GiB UDA image or skipping .autorelabel: Always convert fedora_uda_raw.img with img2simg so cboot fastboot chunks transfers within its RAM buffer, and always touch /.autorelabel when injecting scripts from another host so Fedora’s Enforcing SELinux policy doesn’t block jamboard-touch-init.service.
  • Installing Flatpaks on the 9.4 GiB internal eMMC: GNOME/Freedesktop Flatpak runtimes consume 2–4 GiB on their own. Stick to native dnf RPM packages (rnote, xournalpp, firefox) and keep compress=zstd:3 enabled on Btrfs to preserve ~5–6 GiB of free working space.
  • Attempting NVIDIA tegraflash.py / RCM (APX) mode on a stock Jamboard: Google blew PKC RSA security fuses on the stock Jetson TX1 module, so unsigned BCT/cboot payloads over APX mode are rejected by the BootROM. Always chainload via unlocked cboot (fastboot flash boot ...), and leave SOS (recovery) populated with LineageOS Recovery.

Live Input Capture Findings for the Google Jamboard RAPT Touch Controller (LineageOS)

Overview

These are measurements taken from a live Jamboard running lineage-22.2-20261109-NIGHTLY-baracus_tab (Android 15, kernel 4.9.141, userdebug, SELinux Enforcing), captured over Root ADB from /dev/hidraw*. They replace the size-band assumptions derived from static analysis of the stock ROM and are the basis for the classification in artifacts/jamboard/jamboard-pen-daemon.c.

Captures were taken with a finger, the stock passive stylus (upright and tilted), a substitute whiteboard eraser (the official Jamboard eraser was not available), the heel of a palm, and the stylus with a palm resting beside it. About 34,100 contact rows were analyzed. Small derived artifacts are in artifacts/jamboard/captures/: both HID report descriptors (raw and decoded) and phase-summary.csv. The multi-megabyte raw captures were not committed.

Prerequisites

  • LineageOS baracus_tab with Settings > Developer options > Rooted debugging (ADB only) enabled, then adb root.
  • An unprivileged adb shell (uid 2000) can run getevent but is blocked by SELinux from /dev/hidraw*, /proc/bus/input/devices, dmesg and /sys/kernel/debug/hid. Root is required for any capture.
  • artifacts/jamboard/rapt-live-probe.sh to reproduce the data.

Findings

1. One USB device, two HID interfaces with different descriptors

2986:0137 (“RAPT Touch RAPT Touch”, driver hid-multitouch) exposes usb-70090000.xusb-4/input0 (hidraw0) and /input1 (hidraw1). Both evdev nodes show INPUT_PROP_DIRECT, 24 slots, TOUCH_MAJOR/MINOR 0..14999, POSITION_X/Y 0..29999, PRESSURE 0..29999, and no ABS_MT_TOOL_TYPE, BTN_TOOL_PEN or BTN_TOOL_RUBBER. Android therefore sees every contact as a finger.

hidraw0 (basic)hidraw1 (extended)
Descriptor2,313 B3,149 B
Report 0xF1340 B (24 x 14 B)484 B (24 x 20 B)
Extra input reportnone0xF6, 103 B, contamination map (~33 Hz, streams even when idle)

The basic descriptor matches the stock ROM’s rapt_hid_descriptor.bin except for the physical size. The extended descriptor was not present in the stock ROM dump. Full layouts are in rapt-touch-and-scaler-protocol.md.

2. The firmware classifies every contact

On the extended interface Vendor 0xFF00:0x02 takes the values 1 = stylus, 2 = finger, 3 = eraser/large. It is latched per contact ID and never changed mid-stroke in any capture.

3. Width + Height is exactly constant per class

Firmware classWidth + Height (all rows)
1 stylus12000

3 eraser29998

Height (which equals Vendor 0xFF00:0x01) is the real size measure and Width is class_base - Height. A classifier of Width + Height < 18000 -> stylus, < 27000 -> finger, otherwise eraser reproduced the firmware class with zero mismatches on the stylus, eraser-substitute and pen+palm captures, and also works on the basic interface, which lacks the class field.

Takeaways:

  • Erasers and palms split into several blobs. Eraser and palm frames carry up to 5 simultaneous contacts, and the secondary blobs are often classified as finger next to a class-3 blob. Without clustering they would show up as stray touches. This is why the daemon merges nearby contacts into one eraser group (--eraser-cluster-mm 70).
  • A resting hand beside the stylus was never class 3. In the stylus + palm phase the hand registered only as class 2 (finger), and the stylus stayed class 1.
  • A very tilted stylus can flip to finger class (203 rows) when its contact becomes broad enough. This is a known limitation; wedge/tilt handling is out of scope for now.
  • Tip Pressure is contact area, not force. It rises with palm/eraser contact and reaches 29999.
  • Vendor 0xFF00:0x03 is constant 4096, and 0xFF00:0x04/0x05 duplicate X/Y in all captures.

5. The stock 0.40 / 0.475 size bands do not match live data

Static analysis of libjamkiosk.so found TouchTypeFromSize thresholds of 0.40 and 0.475 on MotionEvent.getSize(). With the live values, 0.5 * (Width + Height) / 14999 is 0.40 (stylus), 0.90 (finger) and 1.00 (eraser): the stylus sits exactly on the stock threshold and finger and eraser both land above 0.475. The stock Google kernel (LNX boot image, not dumped) must therefore remap these HID fields differently from LineageOS’s hid-multitouch. The daemon uses the firmware class or the Width + Height classifier instead, and the former --use-norm-bands option was removed.

6. Other measured facts

  • Physical size is 1207.6 mm x 678.4 mm (descriptor Physical Max 12076 / 6784), not 1210 x 680 as in the stock ROM descriptor.
  • Both interfaces report 0xF1 at ~357 Hz while touched; scan time advances 25 units (2.5 ms) per frame. hidraw0 is silent when idle.
  • hazeldos-ctrl is stopped after boot (init.svc.hazeldos-ctrl=stopped); touch is already powered, and props show ro.boot.touch_panel_id=63.
  • /vendor/etc/input-port-associations.xml maps usb-70090000.xusb-4/input0 to display 0 and /input1 to display 99.
  • /dev/ttyACM0 and /dev/ttyACM1 exist, /dev/ttyTHS1 is root only, and there is no /dev/hidg0.

Common Pitfalls

  • Running the probe without root: cat /dev/hidraw* silently fails under SELinux in an unprivileged adb shell. Use adb root first.
  • Assuming hidraw0 and hidraw1 have the same layout: frame lengths differ (340 vs. 484 bytes) and hidraw1 interleaves 103-byte 0xF6 frames. Parse by report ID and fixed length.
  • Treating Tip Pressure as force: it follows contact area.
  • Using the substitute-eraser numbers as the official eraser’s: the official Jamboard eraser has not been measured. Class 3 should still apply, but this has not been confirmed.

Part 1: RAPT Optical Touchscreen & Stylus/Eraser Subsystem

1.1 GPIO Power-Up & SPIFI Boot Sequence

The internal RAPT Touch controller (VID:PID 1cbe:0003 on Jamboard; 2986:0137 on generic RAPT firmware) is wired to internal Tegra XUSB port usb2-3 (usb-70090000.xusb-4). It remains powered down at cold boot until three Tegra210 GPIOs on gpiochip0 (tegra-gpio) are sequenced:

SignalTegra GPIO Namegpiochip0 OffsetActive StatePurpose
pwren (v12-gpios)TEGRA_GPIO(V, 6)174Active-Low (0 = ON, 1 = OFF)Enables 12V/step-down rail to touch bezel
bootmode (vbus-gpios)TEGRA_GPIO(X, 0)1840 = SPIFI flash, 1 = USB DFUSelects normal SPIFI firmware boot
reset (reset-gpios)TEGRA_GPIO(X, 1)185Active-High (1 = Reset, 0 = Run)Touch MCU hardware reset line

Boot Sequence:

  1. Drive 185=1 (hold reset), 184=0 (select SPIFI), 174=0 (power ON).
  2. Wait 200–250 ms for rails to stabilize.
  3. Drive 185=0 (release reset) while keeping 184=0 and 174=0 asserted.
  4. Within ~1–2 seconds, the controller enumerates on USB with two HID interfaces (input0 and input1) plus CDC ACM serial ports (/dev/ttyACM0, /dev/ttyACM1).

(On LineageOS, /vendor/bin/hazeldos-ctrl spifi_boot performs this automatically at boot. On Fedora, use artifacts/jamboard/systemd/jamboard-touch-init.)

1.2 USB HID Interfaces & Report 0xF1 Wire Specification

The controller enumerates as one USB device (2986:0137, “RAPT Touch RAPT Touch”) with two HID interfaces. On the live LineageOS unit (usb-70090000.xusb-4/input0 and /input1) they present different report descriptors:

InterfaceDescriptor sizeReport 0xF1 sizeContact slotOther reports
Basic (input0)2,313 B (matches stock etc/rapt_hid_descriptor.bin, except physical size)340 B14 BFeature 0xF2, 0x44
Extended (input1)3,149 B (not present in the stock ROM dump)484 B20 BInput 0xF6 (103 B, contamination map, ~33 Hz even when idle), Feature 0xF2, 0x44

Live physical size is 1207.6 mm x 678.4 mm (Physical Max X 12076, Y 6784 in units of 0.1 mm). The stock ROM descriptor says 12100 / 6800; use the live values.

Width encodes the class. In 34,102 captured contact rows, Width + Height is exactly constant per firmware class: stylus 12000, finger 26998, eraser 29998. This matched the firmware class with zero mismatches on the captured data. The firmware latches the class per contact ID, so it does not flip mid-stroke.

Companion HID Feature Reports

  • Feature Report 0xF2 (2 bytes): F2 18 - Contact Count Maximum = 24. (Linux hid-multitouch reads this on enumeration; jamboard-pen-daemon also issues HIDIOCSFEATURE.)
  • Feature Report 0x44 (257 bytes): Windows Touch Hardware Quality Assurance (THQA) signature blob; ignored on Linux/Android.

What the stock Linux input layer does with this

LineageOS’s 4.9 kernel binds hid-multitouch to both interfaces. The resulting evdev nodes expose ABS_MT_TOUCH_MAJOR/MINOR (0..14999), ABS_MT_PRESSURE and ABS_MT_POSITION_X/Y, but no ABS_MT_TOOL_TYPE and no BTN_TOOL_PEN/BTN_TOOL_RUBBER. Android therefore sees every contact as a finger, which is why a daemon that reads the firmware class from hidraw is needed.

1.4 Configuration Step 2: Build & Run jamboard-pen-daemon

artifacts/jamboard/jamboard-pen-daemon.c reads RAPT hidraw frames directly and re-exposes them as two clean uinput devices:

  1. Auto-detects the interface: Prefers the 3,149-byte extended hidraw (firmware class available), falls back to the 2,313-byte basic one with the Width+Height classifier (--sum-classifier forces it; thresholds --sum-stylus-max 18000 / --sum-finger-max 27000). 0xF6 and short reports are skipped.
  2. Grabs raw RAPT evdev nodes (EVIOCGRAB): Prevents the two kernel hid-multitouch devices from emitting duplicate finger touches while writing or erasing. (--no-grab disables this.)
  3. Exposes Jamboard RAPT Finger Touch (uinput, INPUT_PROP_DIRECT): 24-slot Type-B multi-touch screen; touch major/minor come from Height, pressure from Tip Pressure.
  4. Exposes Jamboard RAPT Stylus & Eraser (uinput, INPUT_PROP_DIRECT):
    • BTN_TOOL_PEN + BTN_TOUCH for firmware class 1; ABS_PRESSURE is Tip Pressure scaled to 256..4095,
    • BTN_TOOL_RUBBER + BTN_TOUCH for firmware class 3 (official eraser, any whiteboard eraser, or the heel of a palm), with a short spatial/temporal latch,
    • Spatial eraser clustering (--eraser-cluster-mm 70.0): nearby secondary blobs (knuckles, the other edge of a felt block) are merged into one Height-weighted eraser centroid and suppressed on the finger device until lift-off, so a palm wipe never leaks pan/zoom gestures. The cluster span scales eraser ABS_PRESSURE (1200..4095) from --eraser-base-mm 40.0 up to 180 mm.
    • No tilt axes are emitted: the optical bezel provides no tilt information (see the findings doc).

Part 2: MStar MST9U23T1 Display Scaler UART Protocol (/dev/ttyTHS1)

The 55" 4K panel’s MStar scaler communicates with Tegra210 UART1 (/dev/ttyTHS1, serial@70006040) at 9600 baud, 8N1, raw mode, no flow control.

2.1 Packet Framing & Checksum Formula

Every host-to-scaler command follows DDC2Bi-style framing:

6E  51  <0x80 | payload_len>  <payload_bytes...>  <checksum>

Where the trailing checksum byte is computed across all preceding bytes of the frame seeded with 0xAB:

uint8_t checksum = 0xAB;
for (size_t i = 0; i < frame_len - 1; i++) {
    checksum ^= frame[i];
}

(For the 10-byte Set Brightness command 6E 51 86 03 F5 DD 85 FE <val> <chk>, 0xAB ^ 0x6E ^ 0x51 ^ 0x86 ^ 0x03 ^ 0xF5 ^ 0xDD ^ 0x85 ^ 0xFE == 0xE9, which simplifies to chk = 0xE9 ^ val!)

2.2 Complete MStar Scaler Command Reference

Part 3: RAPT Sensor Processor (/dev/ttyACM1) Management Reference

For completeness, the RAPT controller also exposes /dev/ttyACM1 (115200 8N1 raw), which Google’s rspdaemon (librsp.so) used exclusively for out-of-band diagnostics and firmware updates:

  • Framing: [uint32_le byte_length][Protobuf rsp.Request] → [uint32_le byte_length][Protobuf rsp.Response] (+ XMODEM blocks for file/firmware transfers).
  • Supported rsp.CommandType enums: 1=GET_STRING_PROPERTY, 2=SET_STRING_PROPERTY, 3=GET_VERSION, 4=GET_LEVEL1_STATS, 5=GET_LEVEL2_STATS, 6=GET_LOGS, 7=UPDATE_FIRMWARE, 8=ROLLBACK_FIRMWARE, 9=REBOOT, 10=SET_DATE, 11=SEND_FILE, 12=RECEIVE_FILE, 13=LIST_FILES, 14=DELETE_FILE, 15=RESET_CON_MAP, 16=GET_CON_MAP.
  • Important: Do not run UPDATE_FIRMWARE or RESET_CON_MAP unless recalibrating optical bezel contamination; normal multi-touch, stylus, and eraser streaming over /dev/hidraw* requires zero /dev/ttyACM1 traffic.

Common Pitfalls

  • Not grabbing (EVIOCGRAB) the raw kernel evdev nodes when running jamboard-pen-daemon: Because the kernel still binds hid-multitouch to input0 and input1, leaving them ungrabbed causes every stylus stroke to simultaneously emit phantom finger touches. Always run jamboard-pen-daemon with its default --grab behavior.
  • Switching scaler input to usbc / hdmi1 without a way back: Once switched to an external video input, you won’t see the internal OS until you switch back. Either run jamboard-scaler input internal over SSH/ADB, bind a physical USB keyboard shortcut in GNOME to jamboard-scaler input internal, or power-cycle the Jamboard.
  • Sending out-of-range brightness values (> 100 / > 0x64): While raw bytes up to 0xFF compute a valid XOR checksum, the MStar scaler’s nominal backlight scale is 0..100 (0x00..0x64). jamboard-scaler.sh clamps inputs safely to 0..100.

Automated Expiration Checks

When dealing with many certificates, automation is necessary. Here are several approaches for scripting certificate checks.

Option 1: Multi-Namespace Checking

This script iterates over key namespaces and extracts the end date for all TLS secrets:

#!/bin/bash

NAMESPACES=("openshift-kube-apiserver" "openshift-ingress" "openshift-config-managed")

for ns in "${NAMESPACES[@]}"; do
    echo "======== $ns ========"
    oc get secret -n "$ns" -o json 2>/dev/null | \
      jq -r '.items[] | select(.type == "kubernetes.io/tls") | .metadata.name' | \
      while read secret; do
        echo -n "$secret: "
        oc get secret -n "$ns" "$secret" -o jsonpath='{.data.tls\.crt}' | \
          base64 -d | openssl x509 -enddate -noout | cut -d= -f2
    done
    echo ""
done

Option 2: Comprehensive Warning Script (Recommended)

This script calculates the remaining days for each certificate in a namespace and provides warnings if they are close to expiring. It handles epoch time conversion for robust comparison.

#!/bin/bash

NAMESPACE="openshift-kube-apiserver"
DAYS_WARNING=30

oc get secret -n "$NAMESPACE" -o json | jq -r '.items[] | select(.type == "kubernetes.io/tls") | .metadata.name' | while read secret; do
    echo "=== Certificate: $secret ==="
    
    # Extract and decode certificate
    CERT=$(oc get secret -n "$NAMESPACE" "$secret" -o jsonpath='{.data.tls\.crt}' | base64 -d)
    
    # Get expiration date in seconds since epoch
    EXPDATE=$(echo "$CERT" | openssl x509 -enddate -noout | cut -d= -f2)
    EXPDATE_EPOCH=$(date -d "$EXPDATE" +%s 2>/dev/null || date -j -f "%b %d %T %Y %Z" "$EXPDATE" +%s)
    NOW=$(date +%s)
    DAYS_LEFT=$(( ($EXPDATE_EPOCH - $NOW) / 86400 ))
    
    # Display results
    echo "Expires: $EXPDATE"
    echo "Days remaining: $DAYS_LEFT"
    
    # Warning if expiring soon
    if [ $DAYS_LEFT -lt $DAYS_WARNING ]; then
        echo "⚠️  WARNING: Certificate expires in $DAYS_LEFT days!"
    elif [ $DAYS_LEFT -lt 0 ]; then
        echo "❌ CRITICAL: Certificate has expired!"
    else
        echo "✓ OK"
    fi
    echo ""
done

Note: Save as check-certs.sh, run chmod +x check-certs.sh, and configure it as a cron job for regular monitoring.

Chaining GitHub Actions Workflows Without a PAT or GitHub App

How to trigger one workflow from another when you can’t (or don’t want to) use Personal Access Tokens or GitHub Apps.

The Problem

You have two workflows:

  1. Workflow A — Detects branches and auto-creates PRs against main
  2. Workflow B — Runs tests on PRs opened against main

Manual PRs trigger Workflow B. But when Workflow A creates a PR, Workflow B never runs.

Why This Happens

GitHub Actions has a deliberate security feature:

Actions performed using the default GITHUB_TOKEN do not trigger other workflows.

This prevents accidental infinite loops (Workflow A triggers B triggers A triggers B…). When Workflow A creates a PR using GITHUB_TOKEN, GitHub suppresses the pull_request event that Workflow B listens for.

Mitigation Options

OptionHow It WorksProsCons
Personal Access TokenUse a PAT instead of GITHUB_TOKENSimpleTied to user account, expires, requires secret management
GitHub AppCreate app, use its tokenNot tied to user, fine-grained permissionsRequires app creation/management, may need org admin access
workflow_run triggerWorkflow B triggers on Workflow A completionNo extra tokens, works within default permissionsSlightly more complex logic

Why Not PAT or GitHub App?

In enterprise environments, engineers often:

  • Don’t have permission to create GitHub Apps at the org level
  • Can’t or shouldn’t create PATs tied to personal accounts for shared workflows
  • Face security policies that restrict token creation
  • Need solutions that work within the default GITHUB_TOKEN permissions

The workflow_run approach works entirely within GitHub’s default permission model.

Solution: Using workflow_run Trigger

Instead of Workflow B listening for pull_request events (which won’t fire), have it listen for Workflow A’s completion.

Architecture

┌─────────────────┐         ┌─────────────────┐
│   Workflow A    │         │   Workflow B    │
│ (Auto-Create PR)│         │  (Run Tests)    │
└────────┬────────┘         └────────▲────────┘
         │                           │
         │ completes                 │ triggers on
         │                           │ workflow_run
         ▼                           │
    ┌────────────┐                   │
    │   PR       │───────────────────┘
    │  Created   │   (B finds PR from A's run)
    └────────────┘

Implementation

Workflow A: Auto-Create PR

# .github/workflows/auto-pr.yml
name: Auto Create PR

on:
  push:
    branches:
      - 'feature/**'
      - 'fix/**'

jobs:
  create-pr:
    runs-on: ubuntu-latest
    outputs:
      pr-number: ${{ steps.create-pr.outputs.pull-request-number }}
      pr-url: ${{ steps.create-pr.outputs.pull-request-url }}
    steps:
      - uses: actions/checkout@v4

      - name: Create Pull Request
        id: create-pr
        uses: peter-evans/create-pull-request@v5
        with:
          title: "Auto PR: ${{ github.ref_name }}"
          body: |
            Automated PR for branch `${{ github.ref_name }}`
            
            Created by workflow run: ${{ github.run_id }}
          base: main
          branch: ${{ github.ref_name }}

      - name: Output PR info
        run: |
          echo "Created PR #${{ steps.create-pr.outputs.pull-request-number }}"
          echo "URL: ${{ steps.create-pr.outputs.pull-request-url }}"

# .github/workflows/pr-tests.yml
name: PR Tests

  # Still trigger on manual PRs
  pull_request:
    branches: [main]

  # Also trigger when Auto Create PR workflow completes
  workflow_run:
    workflows: ["Auto Create PR"]

            core.setOutput('pr-head-sha', pr.head.sha);

        uses: actions/checkout@v4

          # Use PR ref for workflow_run, default for pull_request

          echo "Running tests..."
          # Your test commands here

            const prNumber = '${{ steps.pr-info.outputs.pr-number }}';

              owner: context.repo.owner,
              repo: context.repo.repo,
              sha: sha,
              state: 'success',  // or 'failure' based on test results
              context: 'PR Tests (via workflow_run)',
              description: 'Tests passed'
            });

Key Points

  1. Dual triggers: Workflow B responds to both pull_request (manual PRs) and workflow_run (auto PRs)

  2. Conditional logic: The if condition ensures we only run on successful Workflow A completions

  3. PR discovery: Since workflow_run doesn’t have PR context, we query the API to find the PR by branch name

  4. Status reporting: We manually create commit statuses so the PR shows test results

Caveats

Check Runs and PR Status

When triggered via workflow_run, the workflow runs in the context of the default branch, not the PR. This means:

  • PR checks list won’t automatically show the workflow
  • You need to manually create commit statuses (shown above)
  • Or use the Checks API to create check runs

Race Conditions

If Workflow A completes before the PR is fully created (rare but possible), the PR lookup might fail. Add a short delay or retry logic if needed:

- name: Wait for PR to be indexed
  run: sleep 5

Branch Name Matching

The PR lookup uses the head branch. Ensure Workflow A’s branch naming is predictable so Workflow B can find the right PR.

Verification

After implementing:

  1. Push a branch matching your pattern (e.g., feature/test-chain)
  2. Confirm Workflow A runs and creates the PR
  3. Confirm Workflow B triggers on Workflow A completion
  4. Confirm tests run and status appears on the PR

Summary

The workflow_run trigger lets you chain workflows without PATs or GitHub Apps. It’s slightly more complex than the token-based approaches, but works entirely within GitHub’s default permission model — making it ideal for enterprise environments where token creation is restricted.

Fixing Podman Start issues with Krunkit on MacOS

Podman on macOS can run its Linux VM through libkrun via the krunkit binary (installed from Homebrew). When required shared libraries are missing, krunkit crashes immediately and Podman reports an unhelpful abort-trap error instead of the underlying dyld failure.

This guide documents the symptoms, troubleshooting steps, fix, and prevention for that failure mode.

Symptoms

Starting a libkrun-backed Podman machine fails:

podman machine start

Example output:

Starting machine "podman-machine-default"
Error: krunkit was terminated by signal: abort trap

Related indicators:

  • podman machine list shows the machine in stopped state with Never under Last Up
  • podman version fails with a socket/SSH connection error because the VM never started
  • The machine was created with VM type libkrun (default when krunkit is installed)
podman machine list
# NAME                     VM TYPE     ...
# podman-machine-default*  libkrun     ...  Never

Root Cause

krunkit depends on a chain of Homebrew libraries (libkrun-efi, virglrenderer, and others). If any link in that chain is missing, macOS dynamic linker (dyld) aborts the process before Podman can surface a clear error.

In this case, two libraries were not installed:

Missing libraryRequired bySymptom when running krunkit --version
libepoxylibkrun-efiLibrary not loaded: .../libepoxy.0.dylib
molten-vkvirglrendererLibrary not loaded: .../libMoltenVK.dylib

Podman only reported the generic abort trap because krunkit exited before the VM could boot.

Troubleshooting

Work through these steps to isolate the failure.

1. Confirm machine state and provider

podman machine list
podman machine inspect podman-machine-default

Look for VM TYPE: libkrun and State: stopped.

2. Run krunkit directly

This usually reveals the real dyld error:

which krunkit
krunkit --version

If krunkit crashes with Library not loaded, note the missing .dylib path.

3. Check Homebrew dependency tree

brew deps krunkit
brew deps --installed krunkit libkrun-efi

Compare installed deps against what krunkit --version reports as missing.

4. Inspect linked libraries (optional)

otool -L "$(which krunkit)"

Follow the chain into /opt/homebrew/Cellar/ if multiple libraries are missing.

Resolution

Install the missing libraries reported by krunkit --version, then start the machine.

For the missing libepoxy and molten-vk libraries:

brew install libepoxy molten-vk

Verify krunkit runs:

krunkit --version
# krunkit 1.1.1

Start the Podman machine:

podman machine start

If dependencies are still broken or versions are mismatched, reinstall the krunkit stack so Homebrew relinks everything:

brew reinstall krunkit libkrun-efi
podman machine start

Verification

Confirm client–server connectivity:

podman version

Run a test container:

podman run --rm hello-world

Expected: image pulls successfully and prints the Podman hello-world banner.

Prevention

  • Install krunkit from the maintained tap so Homebrew tracks dependencies:

    brew tap slp/krun
brew install krunkit

  • Avoid orphaning dependencies — if you run brew cleanup or manually remove packages, check that krunkit --version still works before starting Podman.

  • After major macOS or Homebrew upgrades, verify the stack:

    krunkit --version && podman machine start

  • Rootless vs rootful — the default machine runs rootless. If you need ports below 1024 or hit Docker-client compatibility issues:

    podman machine set --rootful

HCL BigFix Agent Architecture Guide

Overview

HCL BigFix is a multi-platform endpoint management platform that enables IT operations and security teams to discover, manage, patch, and secure global IT estates. Whether operating on-premises, in the cloud, or in hybrid environments, BigFix uses a unique single-agent, hierarchical architecture to manage thousands of devices efficiently with minimal bandwidth overhead.

This guide is designed for technical consultants planning a new BigFix deployment with a client. It outlines the core architectural components, infrastructure decisions, prerequisite checklists, deployment flows, and discovery questions necessary to align with a client’s requirements.

BigFix Core Architecture & Components

BigFix does not rely on active scanning or heavy database polling. Instead, it operates on a pull-based, “Relevance” evaluation model.

1. The Root Server

The central brain of the deployment. It:

  • Collects and aggregates reports from agents.
  • Downloads patch feeds and fixlets from the HCL Content Servers.
  • Manages and distributes action payloads.
  • Runs the core database services.

2. BigFix Relays

Relays are intermediate staging points. Instead of 10,000 agents downloading a 100MB patch over a WAN link from the Root Server, the local Relay downloads it once, and the local agents fetch it from that Relay over the local LAN.

  • Relays are standard endpoints running a lightweight relay service.
  • Hierarchical layering: Relays can report to other parent relays (Top-Level Relays), shielding the Root Server from direct load.

3. BigFix Client (Agent)

A lightweight agent (~10-20MB RAM, <2% CPU) running as a system service on every managed machine.

  • It continuously evaluates the endpoint state using Relevance Language (a declarative query language).
  • If an agent determines a patch or configuration is “relevant”, it flags itself in the Console.
  • It executes Action Scripts when instructed by the operator.

4. BigFix Console

The primary administrative interface used by operators to view inventory, author actions, and deploy patches.

  • Constraint: The Console is strictly a Windows-only desktop application.
  • It connects directly to the Root Server via HTTP/HTTPS.

5. Web Reports

A web-based interface for secondary reporting, viewing historical trends, and sharing read-only compliance dashboards with executive stakeholders.

Infrastructure Sizing & Database Choices

Selecting the right OS and Database backend is the most critical decision during the initial phase.

Supported Operating Systems for Root Server

  • Windows Server: 2016, 2019, 2022 (Standard and Datacenter editions).
  • Red Hat Enterprise Linux (RHEL): 8.x, 9.x (64-bit).

Database Backends & Constraints

  • Microsoft SQL Server (for Windows Server deployments):
    • SQL Server Enterprise & Standard: Supported for versions 2014 through 2022.
    • SQL Server Express: Supported only for proof-of-concept (POC) environments or environments with fewer than 500 endpoints due to the 10GB database size limit.
  • IBM DB2 (for Linux deployments):
    • DB2 v11.5 is the standard for Linux deployments.
    • An evaluation/bundled version of DB2 is typically included in the Linux server installer.

Configuration & Installation Sequence

The general deployment path follows these distinct phases:

Phase 1: License Authorization & Masthead Creation

  1. Run the BigFix Installation Generator on a Windows staging machine.
  2. Submit your HCL license authorization file (.BesLicenseRequest) to the HCL License server.
  3. HCL returns a Signed License file.
  4. Generate the Masthead file (actionsite.afxm). This file acts as the anchor of trust. It contains the server FQDN, configuration parameters, and the public key used by agents to verify that actions sent to them are authentically signed.

Phase 2: Installing the Root Server

  • On Windows: Run setup.exe and choose “Install Server”. Configure your connection to MS SQL Server and select your generated masthead.
  • On Linux: Extract the tarball, ensure database (DB2/external) is ready, and run:
    ./install.sh
    Select Option [1] All Components or [2] Server and Client Only when prompted.

Phase 3: Deploying the Console

  1. Run the console installer on a Windows administrator workstation.
  2. Connect to the Root Server using the operator account created during server installation.

Phase 4: Deploying Relays

  1. Install the standard BigFix Agent on dedicated relay VMs or branch office hosts.
  2. In the BigFix Console, right-click the designated computers and select “Install BigFix Relay”.
  3. Configure the relay settings (e.g., maximum cache size, parent relays).

Phase 5: Agent Rollout

  • Use the Client Deploy Tool (CDT) built into the Console to push agents over SSH or WMI.
  • For large scale deployments, deploy the agent MSI/RPM package via GPO, SCCM, or Ansible, bundled with the generated actionsite.afxm masthead.

Consultant’s Discovery Checklist

Use these specific discovery questions during your initial meeting with the client to gather architectural requirements:

  1. How many total endpoints (workstations, servers, VMs, containers) are in scope?
    • Why: Determines whether SQL Server Express is acceptable (< 500) and sets hardware specifications.
  2. What is the current distribution of Operating Systems across these endpoints?
    • Why: Identifies if they need specific OS agents and helps plan the deployment method.
  3. What is the network topology? Do you have remote branch offices or bandwidth-constrained links?
    • Why: Drives the relay placement strategy and WAN bandwidth throttle planning.
  4. Do you have a preferred Operating System for the central BigFix server (Windows Server vs RHEL)?
    • Why: Dictates database licensing requirements (MS SQL Server vs DB2) and administrative skillsets.
  5. How are endpoints currently patched or managed? Do we need to plan co-existence or a migration from tools like WSUS, SCCM, or Ansible?
    • Why: Highlights potential software conflicts or open firewall port struggles.
  6. Will endpoints reporting from outside the corporate firewall (remote/WFH workers) need management?
    • Why: Determines if we need to deploy an Internet-Facing Relay (DMZ Relay) with public DNS records.

Common Pitfalls & Anti-Patterns

  • Hardcoding Server Names: Installing with a specific server name (e.g., srv-bf-prod-01) instead of a DNS CNAME alias (bigfix.company.com). If the server hardware dies, migrating the system requires manually updating the masthead on every single agent.
  • Neglecting Relay Cache Limits: Leaving relay cache limits at default values. In environments deploying heavy OS patches or major software rollouts, relays will run out of cache space, causing them to fetch payloads repeatedly across WAN links.
  • Ignoring UDP 52311: Assuming TCP is sufficient. Without UDP 52311 inbound to clients, operators cannot trigger “Instant” actions, severely impacting incident response speeds.
  • Insufficient Space in Temporary Directories: Installing without verifying disk space in /var/tmp (Linux) or C:\Windows\Temp (Windows). BigFix client downloads are staged here, and major patch actions will fail if these directories are constrained.

podman system connection list

Podman exposes a Docker-compatible API so tools and scripts written for Docker can talk to Podman instead. On macOS, Podman Desktop enables Third-Party Docker Tool Compatibility by default.

ls -la /var/run/docker.sock

  1. Ensure the Podman machine is running.

docker info --format '{{.ServerVersion}}'
# Should report a Podman version, not Docker Desktop

export DOCKER_HOST="unix://${HOME}/.local/share/containers/podman/machine/podman.sock"

docker context create podman \
  --docker "host=unix://${HOME}/.local/share/containers/podman/machine/podman.sock"

NVIDIA Container Toolkit & CDI Setup on Proxmox GPU Passthrough VMs

Overview

NVIDIA Container Toolkit with CDI (Container Device Interface) enables Docker containers to access physical GPUs. On Proxmox VMs with GPU PCI passthrough, CDI specs must be explicitly generated and Docker must be configured to use them.

Prerequisites

  • Proxmox VM with NVIDIA GPU PCI passthrough configured (IOMMU, vfio-pci)
  • NVIDIA driver installed and nvidia-smi working on the host
  • Docker installed

Step-by-Step

1. Install NVIDIA Container Toolkit

curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt-get update
sudo apt-get install -y nvidia-container-toolkit

2. Generate CDI Specs

sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml

Verify the spec was created:

ls -la /etc/cdi/nvidia.yaml

3. (If Needed) Create AMD CDI Stub

On Proxmox GPU passthrough VMs, Docker’s CDI resolution may also require an amd.yaml spec. If NemoClaw or other GPU-passthrough tools fail with “AMD CDI spec not found”, create a minimal stub:

sudo tee /etc/cdi/amd.yaml > /dev/null <<'EOF'
---
cdiVersion: "0.5.0"
kind: "amd.com/gpu"
devices:
  - name: "stub"
    containerEdits:
      env:
        - ROCR_VISIBLE_DEVICES = ""
EOF

4. Configure Docker for CDI

sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

5. Verify GPU Access

docker run --rm --gpus all nvidia/cuda:12.0-base nvidia-smi

You should see the GPU listed with driver version and CUDA capabilities.

Set OS_TAG to rhcos4.<minor> matching your OpenShift workers (NVIDIA documents this pattern).

Set PRIVATE_REGISTRY to the registry host and namespace prefix you will push to. For the integrated registry, that is commonly the external route hostname (for pushes from your workstation) plus project path, for example:

default-route-openshift-image-registry.apps.<cluster-base>/<project>

…where <project> is often nvidia-gpu-operator or a dedicated images project. See using-integrated-openshift-registry.md for login and push mechanics.

Example (illustrative only — adjust host, project, and versions):

export VERSION=510.73.06
export OS_TAG=rhcos4.15
export PRIVATE_REGISTRY=default-route-openshift-image-registry.apps.cluster.example.com/nvidia-gpu-operator

Build and push using podman or docker as in NVIDIA’s doc:

podman build --build-arg DRIVER_VERSION="${VERSION}" \
  -t "${PRIVATE_REGISTRY}/vgpu-manager:${VERSION}-${OS_TAG}" .
podman push "${PRIVATE_REGISTRY}/vgpu-manager:${VERSION}-${OS_TAG}"

Use a meaningful tag (here ${VERSION}-${OS_TAG}) so ClusterPolicy and support tickets stay unambiguous.

4. Reference the image from in-cluster pulls

Operands pull using the in-cluster registry DNS (typically image-registry.openshift-image-registry.svc:5000/<project>/vgpu-manager:<tag>). Your ClusterPolicy vgpuManager.repository / image / version (or equivalent fields) must match how your installed GPU Operator version assembles the pull spec. Always confirm with:

oc explain clusterpolicy.spec.vgpuManager --recursive

Conceptually you are wiring repository + image + version so they resolve to the same image you pushed (often image: vgpu-manager, version: tag string like 510.73.06-rhcos4.15 if that is what you pushed).

5. Update ClusterPolicy (operator already installed)

Generate or export the example ClusterPolicy, then merge at least:

  • spec.sandboxWorkloads.enabled: true
  • spec.sandboxDevicePlugin.enabled: true
  • spec.vgpuManager.enabled: true with repository, image, version, and imagePullSecrets if your registry requires them
  • spec.vgpuDeviceManager.enabled: true

NVIDIA’s JSON-oriented example is in Creating a ClusterPolicy for the GPU Operator using the CLI. If a ClusterPolicy already exists, prefer oc get clusterpolicy -o yaml, edit, and oc apply.

6. Verify

oc get clusterpolicy -o yaml | less
oc get pods -n nvidia-gpu-operator
oc get nodes -l nvidia.com/gpu.workload.config=vm-vgpu

When the vGPU Manager and sandbox operands are healthy and nodes are labeled, continue with NVIDIA’s HyperConverged mediated device steps and VM attachment.

Common pitfalls

  • Wrong vgpu-manager subdirectory or OS_TAG for your RHCOS line → build succeeds but driver mismatches the node OS.
  • ClusterPolicy fields do not match the pushed tag → ImagePullBackOff on daemonsets or operator-managed pods.
  • Image in project A, operands in nvidia-gpu-operator without system:image-puller (or a pull secret) → pull forbidden across namespaces.
  • Enabling vgpuManager before the image exists → transient failures; enable or point after push.

Using the integrated OpenShift container image registry

OpenShift ships with a cluster-internal container registry (the Image Registry Operator, namespace openshift-image-registry). You can push images there instead of an external registry (for example Quay.io), as long as workloads that need the image can pull from the namespace where the image lives.

This is the same pattern NVIDIA documents for hosting built images (for example vGPU Manager) on the cluster’s own registry.

What you get

  • In-cluster pull hostname (from any pod on the cluster):

    image-registry.openshift-image-registry.svc:5000

  • Full image reference:

    image-registry.openshift-image-registry.svc:5000/<project>/<image>:<tag>

    Example: image-registry.openshift-image-registry.svc:5000/nvidia-gpu-operator/vgpu-manager:9.0.0.0

  • Private by default: images are not public on the internet; access is via Kubernetes RBAC and image pull credentials where needed.

Prerequisites

  1. Registry is running — ManagementState should be Managed:

    oc get configs.imageregistry/cluster -o jsonpath='{.spec.managementState}{"\n"}'

  2. Storage — the registry needs a PVC or other supported backend (install-time or day-2 configuration). If the registry is not ready, pushes fail until storage is fixed.

  3. Pushing from your laptop — you need a route (or port-forward) and authentication. Check for the default route:

    oc get route -n openshift-image-registry

    If there is no route, an admin can enable the default route or you can push from a Job or Build inside the cluster that uses the internal service DNS and a service account token.

Basic workflow: push an image to the integrated registry

  1. Create or pick a project (namespace) to hold the image, for example nvidia-gpu-operator or a dedicated gpu-images project.

  2. Log in to the registry from your workstation (using the external route host Red Hat documents for your version), with an OpenShift user token:

    REGISTRY=$(oc get route default-route -n openshift-image-registry -o jsonpath='{.spec.host}')
podman login -u "$(oc whoami)" -p "$(oc whoami -t)" "$REGISTRY"

    Use docker instead of podman if that is what you use.

  3. Tag and push using the external host for the push client (OpenShift documents the exact hostname pattern; it is often default-route-openshift-image-registry.apps.<cluster-domain>).

    podman tag mylocal/vgpu-manager:9.0.0.0 "$REGISTRY/nvidia-gpu-operator/vgpu-manager:9.0.0.0"
podman push "$REGISTRY/nvidia-gpu-operator/vgpu-manager:9.0.0.0"

  4. Reference the image from manifests using the in-cluster form (*.svc:5000/...) so nodes and pods resolve it without depending on the apps route from inside the cluster.

Use explicit tags (for example 9.0.0.0 or a driver version string), not only latest, so rollbacks and support questions stay clear.

Pulling from another namespace (for example GPU Operator operands)

If the image lives in project gpu-images but pods run in nvidia-gpu-operator, those pods need permission to pull. Typical approaches:

  • Grant the nvidia-gpu-operator default service account (or the operand SA) access to pull from the other namespace (for example oc policy add-role-to-user system:image-puller system:serviceaccount:nvidia-gpu-operator:default -n gpu-images), or
  • Copy/mirror the image into nvidia-gpu-operator and reference it there, or
  • Use an image pull secret in nvidia-gpu-operator that can authenticate to the registry (often unnecessary for same-cluster internal pulls when RBAC is set correctly).

Exact policy depends on your org’s security model; the important part is: internal registry does not remove the need for RBAC across namespaces.

Wiring operators (example: NVIDIA ClusterPolicy / vgpuManager)

Point repository, image, and version (and imagePullSecrets if you use them) at the integrated registry path the same way you would for Quay. The operator concatenates fields according to its CRD; confirm with:

oc explain clusterpolicy.spec.vgpuManager --recursive

Conceptually you want the operands to pull something equivalent to:

image-registry.openshift-image-registry.svc:5000/<project>/<image>:<tag>

Verification

oc get configs.imageregistry/cluster -o yaml | less
oc get route -n openshift-image-registry
oc get imagestream -n nvidia-gpu-operator   # if you use ImageStreams; direct push without IS is also common

pip install ansible-lint

Authentication: Personal Access Tokens (PAT)

In an enterprise environment, you will typically use a Personal Access Token (PAT) instead of your account password for Git operations over HTTPS.

Generating a PAT (GitHub Example)

  1. Log in to your GitHub account.
  2. Go to Settings > Developer settings > Personal access tokens > Fine-grained tokens (or Tokens classic).
  3. Click Generate new token.
  4. Give it a descriptive name (e.g., “VSCode Enterprise Desktop”).
  5. Select the required scopes (typically repo for full control of private repositories).
  6. Copy the token immediately. You will not be able to see it again.

Using the PAT

When you clone a repository or push changes for the first time, Git will prompt for your credentials.

  • Username: Your GitHub username.
  • Password: Paste your PAT here.

Note: On Windows and macOS, the system credential manager will securely store this token for future use.
